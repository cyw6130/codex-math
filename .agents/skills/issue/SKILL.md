# 共享 Issue

## 目标与边界

只处理产品或工程 Backlog 的候选事项，或已完成的产品/工程变更通告。保留用户输入的原始 seed，协助形成可讨论的候选条目，并在用户明确授权后发布到当前仓库的 GitHub Issues。变更通告必须保留事实与证据，不把已完成工作伪装成待办或未来方案。

不要实现事项、修改仓库代码或文档、创建分支或 PR、改变权威数学状态，也不要把 GitHub Issue 当作数学真值。数学目标、证明状态及接纳仍由本套装既有研究合同管理；本技能只记录相关产品或工程需求。

## 开始前读取事实

1. 从 `$issue` 调用中捕获非空 seed；逐字保留它，不把原文只留在聊天摘要中。把它放进草稿的“原始 seed”段落，并在发布的 Issue 或补充评论中保留。
2. 先读取当前工作树的 `docs/agents/issue-tracker.md`，以其中的 GitHub、共享 Backlog、标签和命令约定为准；不要复制或猜测另一套 tracker 规则。
3. 运行 `git remote get-url origin`，把当前 remote 规范化为运行时的 GitHub `owner/repo` 值并验证目标。不得把 owner、repo 或固定 Issue 编号硬编码到 Skill。若没有可用的 GitHub remote，仍可整理草稿，但不得发布。
4. 若条目类型为已完成变更，先从用户给定或环境可确定的 commit、PR、diff、文件变更读取事实，确定确切变更范围、影响与证据链接；按需只读本地 Git 和 GitHub 元数据。找不到确切范围时，才通过 `$grilling` 请用户选择要通告的变更范围，不让用户重复可查事实。

输入为空、remote 无法确认或 `gh` 无权限时，不编造事实；保留当前草稿并明确说明无法发布的原因。

## 唯一提问 primitive：`$grilling`

本仓库使用 [grilling](../../../skills/grilling/SKILL.md)；通过符号链接使用时先解析真实路径。所有需要提出者回答的问题，包括类型判断、补充决定、重复项取舍和最终发布确认，都必须调用并遵循外部 `$grilling`。不要另写问卷、普通追问或自定义提问格式；环境事实由 Agent 查询，不让用户提供本可查到的事实。

启动 `$grilling` 时，把下面的判断作为第一轮第一项；此前不得向用户提出别的问题：

```text
❓ **Q1** - **条目类型**：这段 seed 属于早期“想法”、已有“规划/设计”，还是“已完成变更/变更通告”？

➡️ 推荐：尚未形成具体方案时选“想法”；已有用户、范围、决定或验收描述但尚未完成时选“规划/设计”；seed 描述已经发生的变更时选“已完成变更/变更通告”，并优先用 commit、PR、diff 或文件变更核实事实。
```

按 `$grilling` 的 design tree 和轮次推进，直到当前分支足以形成候选 Backlog 条目。保留提出者的判断，不替提出者做产品决定；未决定的内容写成“未决”，不要用推测填空。

### 早期“想法”分支

只追问形成候选条目所需的最小信息：

- 为什么需要，当前痛点或机会是什么；
- 期望结果是什么；
- 需要的材料、依赖或未知项是什么。

达到这三类信息足以供团队分诊后即停止，不把想法逼成完整 spec、实现方案或承诺。

### “规划/设计”分支

在不代替提出者决策的前提下，进一步核对：用户与工作流、范围和明确非目标、关键决定、验收条件、依赖、风险及未决项。只核对当前设计树需要的内容；不要为了形式完整而发明实现细节。

### “已完成变更／变更通告”分支

先由 Agent 调查事实，再通过 `$grilling` 只追问必要的人类决定：

- 改了什么、确切范围、影响与证据由 Agent 从 seed 指定或环境可确定的 commit、PR、diff、文件变更读取；保留 commit/PR 等证据链接。未验证的完成、测试或影响不得写成事实。
- 只有仍找不到确切变更范围时，才通过 `$grilling` 请提出者选择要通告的范围，不让其复述 Agent 已查到的事实。
- 为什么这次变更值得通知；
- 要通知哪些协作者，使用已确认的 GitHub handle；不能从事实安全确定的 handle 才询问；
- 协作者仅需知情，还是需要审查、迁移或其他明确行动；把行动写清楚，不把通告改写成未来待办。

## Grilling 后查重

`$grilling` 的设计树收口后、生成最终草稿前，读取所有开放 Issues 查重。按 `docs/agents/issue-tracker.md` 的约定运行等价查询，例如：

```bash
gh api --paginate "repos/$repo_slug/issues?state=open&per_page=100" --jq '.[] | select(.pull_request == null) | {number, title, body, labels: [.labels[].name]}'
```

`repo_slug` 必须来自当前 remote。分页读完开放 Issue；对可能相关项再用 gh issue view --comments 读取讨论。根据标题、正文和语义判断高度相似项，不只按关键词判断。对候选项用 `gh issue view "$number" --repo "$repo_slug" --json url --jq .url` 取得真实链接并展示。

发现高度相似项时，先展示链接与相似原因，再通过 `$grilling` 让提出者选择“补充哪个旧 Issue”或“新建 Issue”；未得到选择不得写入。选择补充时只准备一份补充评论，不静默改写旧正文、标签或 assignee。

对已完成变更，先用 seed 和证据核对关联的原 Issue 或 PR；关联项只作为证据链接。变更通告始终新建独立 Issue，不作为旧 Issue 的评论，也不擅自改写关联项的正文、标签、负责人或状态。

## 生成中文草稿

草稿标题应忠实概括 seed，不添加未确认的范围或承诺。正文至少包含以下段落，并保留原始 seed：

```markdown
## 为什么需要

## 期望结果

## 补充材料

## 原始 seed

## 未决项
```

“想法”分支只填上述最低集合；缺少的材料明确写“未提供”或“待补充”。“规划/设计”分支按已有回答增补“用户与工作流”“范围”“非目标”“关键决定”“验收”“依赖与风险”，不把未回答项伪装成已定决定。补充旧 Issue 时，使用同样的事实边界生成评论，并指向被补充的 Issue。

“已完成变更／变更通告”分支的标题直接使用忠实标题，不添加 `[变更通告]` 等类型前缀；类型由 `change-notice` 标签表达。正文至少包含：

```markdown
## 改了什么

## 为什么重要

## 影响范围

## 证据

## 合作者需要做什么

## 原始 seed

## 未决项
```

“改了什么”“影响范围”和“证据”只写已核实事实；证据应保留 commit、PR 等链接，只有文件变更时保留路径和 diff 依据。“合作者需要做什么”明确区分仅知情与审查、迁移或其他行动。不得声称未验证的完成或测试。

## 发布确认与写入

把目标仓库、查重结果以及完整标题和正文（或旧 Issue 的评论）原样展示给提出者。设计草稿通过后，再用 `$grilling` 提出唯一的明确确认：这份内容是否准确代表双方 shared understanding，并授权发布到当前仓库的共享 Issue？只有明确同时同意“理解准确”和“允许发布”才继续；沉默、含糊同意、只同意修改或只同意理解都不算授权。需要修改时回到 `$grilling`，重新展示草稿，不写入。变更通告正文中只 @ 已确认的 GitHub handle，不猜测或补写未确认的 handle。

将已确认正文原样写入临时 UTF-8 文件，body_file/comment_file 指向该文件；不经 shell 插值拼接正文。发布前按 tracker 核对所需标签。新建“想法”或“规划/设计” Issue 时使用运行时解析出的仓库值：

```bash
gh issue create --repo "$repo_slug" --title "$title" --body-file "$body_file" --label needs-triage
```

默认只加 `needs-triage`，不传 `--assignee`。选择补充旧 Issue 时，确认后使用 `gh issue comment "$number" --repo "$repo_slug" --body-file "$comment_file"`，不新建重复 Issue，也不擅自改变旧 Issue 的标签或负责人。

已完成变更无论是仅告知还是需要后续行动，都使用 `gh issue create --repo "$repo_slug" --title "$title" --body-file "$body_file" --label change-notice` 新建独立 Issue，并保持 open。协作者需要审查、迁移或执行其他行动时，在正文中明确列出；关联 Issue 或 PR 只作为证据链接，不以评论替代通告。

命令成功才返回 GitHub URL；补充评论至少返回被补充 Issue 的 URL。认证、权限、网络或 `gh` 失败时，保留完整草稿和原始 seed，明确报告“未发布”或“未补充”，绝不声称成功。结果不确定时先只读核查，不盲目重试造成重复写入。

## 完成条件

- 原始 seed、提出者分支判断和所有未决项仍可从草稿恢复；
- 已按当前 `issue-tracker.md` 查重并展示相似 Issue（如有）；
- 已展示最终草稿并取得明确 shared-understanding / 发布确认；
- 仅在确认后完成对应的 Issue 创建或补充评论，或诚实报告未写入及原因；
- 已完成变更以无类型前缀的忠实标题、`change-notice` 标签和 open 状态发布为独立 Issue；关联 Issue 或 PR 仅作为证据链接。

不把草稿、Issue 标签、Issue 开关 解释为数学结论；不在本 Skill 中添加数学状态、路线状态或平行任务清单。
