# 最小记录与验收

优先复用现有形式化工程与记录，不为满足目录模板迁移工程。新工程通常位于 `formalization/`；只在用户选定目标并授权实施后建立 Lean 工程。记录保存三类材料：代码、对应与进度、实际验证证据。

## 对应与进度

使用一份易维护的 JSON 或 Markdown 台账，至少能回答：

- 本次范围、准确文章路径/哈希、结果稳定 ID/锚点；可选地图版本与对应 ID。
- Lean 文件、声明全名、核心定义、直接实现依赖及外部库声明；阶段性假设和未完成义务。
- Lean 工具链、固定 Mathlib 提交、执行主机、实际检查命令。
- 独立陈述审核者与报告、所审代码快照；用户确认的关键决定。
- 每个目标分别记录：陈述审核（未审/需修订/通过）、形式验证（未执行/进行中/阻塞/条件性已验证/完整已验证）、数学理解及 Lean 熟悉度（由用户反馈确认；未知就记未知）。

学习状态不影响证明真假，不从用户沉默推断理解。论文结果与多个 Lean 辅助声明可以一对多；不要把代码声明计数当论文结果数。文章或代码改变后沿实际依赖判断哪些旧检查失效，旧快照的真实结果保留。

## 验证证据

保存真实命令、工作目录、退出码、完整日志和源文件内容哈希清单（或 Git commit 加未提交改动身份），绑定 lean-toolchain、lakefile、lake-manifest 与所用本地依赖。远程结果绑定所发送快照，返回后核对本地是否已改变；过期成功不能算当前成功。记录可按每次检查一个目录保存，不覆盖先前失败。

实际使用工程已有验证入口。通常 `lake build` 检查默认目标，但它可能不包含选定声明，故另用确实导入所选模块的审计文件，通过 `lake env lean <审计文件>` 或工程等效入口执行。新环境先核对该版本支持的实际命令和已有工具，不能仅复制命令后称已执行。

对每个最终目标检查 `#print axioms 完整声明名` 或等效递归公理收集；检查传递依赖中的 `sorryAx` 与自定义公理，不只搜索目标文件的 sorry 文本。源码搜索只作补充。复用现有允许公理政策；新工程可采用标准逻辑公理 `propext`、`Classical.choice`、`Quot.sound` 的明确基线。任何其他信任来源（包括决定计算的额外信任机制）单独披露并由用户决定，不为通过修改审计白名单或构建配置。

完整验证必须同时满足：
1. 准确快照的完整构建和选定目标加载成功；未验证的默认构建盲区已处理。
2. 最终目标及所需传递依赖无 sorryAx、未获准自定义公理或其他未完成证明。
3. 临时新增假设已在实际对象上兑现，或原目标本就包含这些条件；否则仅报告条件性验证。
4. 最终核心定义与陈述忠实性审核仍适用；使用另一证明时说明对原文路线的覆盖边界。

阶段性目标可以合法地依赖显式假设，但须列出剩余义务，不宣称论文目标完整验证。无 Lean 或远程不可达时仅报告蓝图/代码草稿状态。没有用户选定目标时，安装技能本身不创建“验证通过”记录。
